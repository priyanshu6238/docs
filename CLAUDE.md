# glific/docs

Docusaurus-based user-facing documentation for Glific. Product source lives in the
separate `glific/glific` (backend) and `glific/glific-frontend` (frontend) repos.

## Structure and ordering

- The sidebar is auto-generated from the filesystem (`sidebars.js` → `{ type: "autogenerated", dirName: "." }`).
  Page/folder order is controlled purely by a numeric prefix in the file or folder name,
  e.g. `docs/3. Product Features/02. Speed Sends.md`. When adding a new page to an
  existing category, pick the next free number in that folder; when adding a new
  top-level category, add a `_category_.json` alongside it:
  ```json
  { "link": { "type": "generated-index" } }
  ```
- Don't add Docusaurus front matter (`sidebar_position`, etc.) purely to control
  ordering — this repo uses filename numbering instead, not front matter.

## Page conventions

- Start each page with a read-time + difficulty blockquote, matching neighboring pages, e.g.:
  `> ### **2 minutes read &nbsp;...&nbsp; \`Beginner\`**` (levels used: `Beginner`,
  `Intermediate`, `Advanced`).
- Follow with a one-sentence summary of what the feature does, then `##` sections per
  sub-workflow (e.g. "Create X", "Save X"), with numbered steps as an ordered list.
- Reference exact UI labels, buttons, and field names in backticks as they appear in
  the product (e.g. `` `Quick tools` ``, `` `+Create` ``, `` `Title` `` field) — write
  steps as direct imperative instructions ("Click `Save`", "Enter the message in the
  `Message` field"), not passive descriptions.
- Don't guess at UI behavior — verify against `glific-frontend` (or the running app)
  before describing a click path or field name.

## Screenshots

- Older pages embed screenshots as `<img>` tags pointing at GitHub-hosted attachment
  URLs (`https://github.com/glific/docs/assets/.../<uuid>`) — these come from pasting
  images directly into the GitHub web UI and can't be reproduced by a script or by
  Claude running non-interactively.
- For anything generated by automation (see below) or written without access to that
  upload flow, use a local file under `static/img/generated/` referenced with a path
  *relative to the doc file*, not a site-root path (`![alt text](../../static/img/generated/<path>.png)`,
  not `/img/generated/<path>.png`). A relative path renders correctly both in GitHub's
  raw `.md` view (it resolves against the real file tree) and on the built Docusaurus
  site regardless of `baseUrl` (relative image paths become bundled webpack assets,
  which bake in `baseUrl` automatically — a root-absolute path wouldn't). This is an
  intentional, accepted deviation from the older `<img>`-tag style, not a mistake to
  "fix" by trying to match it.

## Automation

- `.github/workflows/auto-docs.yml` runs when an issue is labeled `auto-docs`: it reads
  the issue, checks out `glific/glific` and `glific-frontend` for context (or a specific
  PR branch, if the issue links one), has Claude update the relevant doc page(s),
  captures fresh screenshots from a staging Glific instance via
  `.github/scripts/take-screenshots.mjs`, and opens a PR for human review. It never
  merges on its own.
- In that workflow, screenshot placeholders use the form
  `![](SCREENSHOT:<slug>:<route-path>)` inside the doc source — the screenshot script
  replaces these after capture. Don't use this placeholder syntax outside that pipeline.
  If the target needs interaction beyond "load the route and shoot" (a dialog behind a
  button click, a dropdown, typed text), pair it with
  `.github/screenshot-steps/<slug>.json` — an array of `{click|fill|wait|waitText|sleep}`
  steps run before the screenshot, deleted afterward (never committed). Selectors in
  that file must come from a real `data-testid` Claude found in `glific-frontend`
  source, never a guess — for targets with no stable selector in source (e.g. a
  dynamically-generated flow-editor canvas node), the correct move is to skip the
  screenshot and say why, not write a steps file likely to fail at runtime.
- `.github/workflows/auto-docs-comment.yml` handles follow-up: commenting `@claude ...`
  on a PR the pipeline opened (must carry the `auto-docs` label, and the commenter needs
  write access) re-invokes Claude on that PR's branch with the comment as the prompt. Works
  both as a general PR conversation comment and as an inline review comment attached to a
  specific diff line — in the inline case Claude also gets the file/line/diff hunk as
  context, and the reply lands in that same inline thread instead of the main conversation.
  It pushes any doc edits directly to the existing branch (no new PR) and replies with what
  it did. Same `docs/`-only guardrail and screenshot placeholder convention apply.
